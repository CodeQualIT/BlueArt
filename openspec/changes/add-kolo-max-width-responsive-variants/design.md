# Design: Add Kolo max-width responsive variants

## Context

The proposal adds Tailwind-compatible max-width responsive variants so responsive
utility ownership can continue moving from `:app` page CSS to co-located Kolo DSL
usage. Kolo currently supports state variants and the mobile-first `sm` through
`2xl` min-width variants only. Every utility family independently recognizes the
same min-width map, and `StyleGeneratorHook.emitVariantRule` always emits
`@media (min-width: ...)`.

Browse and art stylesheets, generated by `CssController`, retain three responsive
exceptions because that model cannot express them:

- at `max-width: 960px`, browse changes its grid and resets the sidebar position;
- at `max-width: 640px`, browse changes the content-top flex direction and
  alignment;
- at `max-width: 700px`, art reduces layout/card/comment padding.

The change crosses `:libs:kolo-styles` token parsing, typed DSL/runtime token
collection, CSS generation, and `:app` render/CSS ownership. It must retain the
existing deterministic token URL, permissive compiler diagnostics, and
side-by-side `kolo.css` plus generated page stylesheet delivery. Stakeholders are
Kolo maintainers, browse/art UI maintainers, and reviewers responsible for
responsive visual parity.

Motivation and scope are defined by
[`proposal.md`](proposal.md). The implementation contract is in the change
specifications for `kolo-max-width-variants`,
`kolo-utility-architecture`, `kolo-css-generation`,
`kolo-html-runtime-integration`, and `generated-page-stylesheets`.

## Goals / Non-Goals

**Goals:**

- Add named `max-*` responsive variants to every existing supported Kolo utility
  family through the established typed parser/generator pipeline.
- Preserve state-variant composition, canonical token collection, and deterministic
  stylesheet output for max-width tokens.
- Provide typed, discoverable DSL access to the variants at browse and art render
  sites.
- Move only declarations whose utility and breakpoint semantics can be represented
  exactly, removing the corresponding duplicate page-CSS declaration in the same
  migration.
- Keep unsupported utilities, selector-dependent rules, and non-equivalent
  breakpoints explicit as `kolo-exception` page CSS.

**Non-Goals:**

- Arbitrary responsive values or CSS-variable breakpoint syntax such as
  `max-[700px]:...`.
- A general application breakpoint-configuration API or new responsive utility
  families.
- Changing existing min-width variant behavior, canonical ordering, request URL
  format, endpoint paths, cache strategy, or diagnostic format.
- Altering unrelated browse/art visual design or forcing a complete page-CSS
  migration.

## Decisions

### 1. Model breakpoint direction as shared variant metadata

**Decision:** Replace the min-width-only media metadata with a shared responsive
variant representation containing the canonical variant name, direction
(`min` or `max`), and CSS boundary. All parser hooks will use this one allow-list,
and `StyleGeneratorHook` will emit the media query from its direction rather than
assuming `min-width`.

**Rationale:** Responsive variants are cross-cutting syntax, not a property of
spacing, layout, font, or sizing. A shared model prevents the current duplicated
per-family maps from accepting different variant sets or generating different
media semantics.

**Alternatives considered:**

- Add a separate max-width map and parsing branch to each utility family:
  rejected because it repeats variant validation and will drift as families grow.
- Implement max-width parsing only in the spacing/layout hooks needed today:
  rejected because the capability specification requires typed Kolo support, not
  a property-specific workaround.
- Put media-query selection in `KoloCssCompiler`: rejected because parser/generator
  hooks own typed token interpretation and CSS emission.

### 2. Use named Tailwind-compatible `max-sm` through `max-2xl` variants

**Decision:** Add `max-sm`, `max-md`, `max-lg`, `max-xl`, and `max-2xl` beside the
existing named min-width variants. Their upper bounds use exclusive Tailwind-style
range semantics: `width < 40rem`, `width < 48rem`, `width < 64rem`,
`width < 80rem`, and `width < 96rem`, respectively. The generator will serialize
the range deterministically in CSS.

**Rationale:** Named variants provide a typed, auditable API and predictable
composition such as `max-sm:...` or `hover:max-md:...`, while exclusive ranges
avoid simultaneous min/max rules at a breakpoint boundary.

**Alternatives considered:**

- Inclusive `max-width` queries at the named breakpoint: rejected because they
  overlap the matching min-width variant and diverge from Tailwind range behavior.
- Arbitrary `max-[value]` syntax: rejected because arbitrary values are excluded
  from Kolo's token model and would weaken validation/caching guarantees.
- Keep max-width behavior in `CssController`: rejected because it leaves a
  recurring utility-ownership gap.

### 3. Keep exact legacy breakpoints unless an equivalent named range exists

**Decision:** Do not approximate the existing 960px or 700px rules with nearby
named `max-*` breakpoints. The 640px content-top rule may migrate only if the
selected `max-sm` serialized boundary is proven visually and semantically
equivalent to the existing rule; otherwise it also remains a marked exception.
The 960px browse grid declaration remains page CSS because its
`grid-template-columns` value has no current utility parity. The sidebar reset and
art padding rules migrate only when both an exact breakpoint and a direct utility
mapping are available; otherwise they stay in `CssController`.

**Rationale:** Matching a nearby 768px or 1024px threshold would silently change
the responsive layout. Retaining an explicit exception is safer than claiming
utility ownership with changed behavior.

**Alternatives considered:**

- Add app-specific `max-700` and `max-960` variants now: rejected because it
  expands a Tailwind-compatible named capability into application breakpoint
  configuration without a reusable configuration contract.
- Approximate 700px as `max-md` and 960px as `max-lg`: rejected because those
  breakpoints change the viewport range in which users see the overrides.
- Migrate page rules while retaining duplicate CSS as a fallback: rejected because
  duplicate ownership causes precedence ambiguity and masks regressions.

### 4. Keep the DSL generic; variants remain chained scopes

**Decision:** Expose max-width variants through the existing `variant(name)` scope
mechanism and add cohesive DSL helpers only where they improve typed
discoverability. Helpers must work on both `KoloScope` and `KoloVariantScope` and
produce the same canonical raw token form as direct variant chaining.

**Rationale:** The runtime already collects arbitrary canonical token strings and
supports chained scopes. Reusing it limits the change to validated compiler
support and avoids changing class naming, request-local collection, or URL
finalization.

**Alternatives considered:**

- Add a separate responsive DSL mechanism: rejected because it would duplicate
  scope chaining and create inconsistent state/media composition.
- Expose raw string tokens only: rejected because the project uses typed DSL
  helpers to avoid spelling and supported-value errors.

### 5. Migrate ownership selector-by-selector under dual stylesheet delivery

**Decision:** Update browse/art `kolo { ... }` call sites and remove exactly the
matching generated CSS declaration in the same change. Retain any unmatched
declaration with a `kolo-exception` marker. Keep `kolo.css` linked alongside
`browse.css` and `art.css`.

**Rationale:** Incremental ownership transfer preserves rollback simplicity and
the migration architecture defined for Kolo. It also keeps `CssController` an
accurate inventory of behavior not yet expressible by utilities.

**Alternatives considered:**

- Big-bang responsive stylesheet conversion: rejected because it increases visual
  regression blast radius.
- Remove all max-width CSS before utility parity exists: rejected because it
  breaks responsive behavior.

## Risks / Trade-offs

- [Exclusive Tailwind boundaries differ from legacy inclusive `max-width: 640px`]
  → Mitigation: verify the boundary at the exact viewport threshold; retain the
  legacy declaration if parity is not exact.
- [Duplicated variant parsing permits inconsistent family behavior] → Mitigation:
  centralize supported responsive metadata and require all parser hooks to use it.
- [State and max-width variant composition emits an incorrect selector or media
  rule] → Mitigation: cover base, state-only, max-only, and chained state/max
  tokens in parser, generator, endpoint, and runtime tests.
- [Migration changes stylesheet precedence or leaves duplicate declarations] →
  Mitigation: remove a declaration only in the same selector migration and extend
  `CssControllerTest` ownership assertions.
- [960px/700px exceptions remain and reduce apparent migration progress] →
  Mitigation: label them with `kolo-exception` and defer them to a dedicated,
  configurable-breakpoint capability rather than approximating behavior.
- [Generated CSS query formatting is unstable] → Mitigation: use typed dimensions
  and exact-output tests to lock the serialized query and escaped token class.

## Migration Plan

1. Inventory each responsive declaration, its render element, property utility
   mapping, and exact breakpoint semantics.
2. Introduce shared directional responsive variant metadata while preserving all
   existing min-width token parsing and generated output.
3. Add the named `max-*` allow-list, typed token metadata, parser validation, and
   direction-aware media emission across all registered utility families.
4. Add or extend DSL variant helpers/scopes for both base and nested variant
   contexts without changing token canonicalization or runtime link generation.
5. Add focused tests for accepted/rejected max tokens, exclusive media output,
   state composition, mixed utility compilation, endpoint diagnostics, and
   rendered class/href collection.
6. Migrate only responsive declarations with exact utility and breakpoint parity;
   remove their duplicate `CssController` declarations and add ownership tests.
7. Keep the 960px grid rule and all non-equivalent breakpoint/property cases as
   documented `kolo-exception`s in page CSS.
8. Run the existing targeted Gradle and Playwright visual-regression lanes across
   the legacy breakpoint boundaries.
9. Deploy using the existing dual-stylesheet delivery. Roll back an affected
   migration by restoring its page-CSS declaration and removing its render-site
   Kolo token; the compiler change itself can be rolled back independently because
   unsupported tokens retain diagnostic behavior rather than failing a response.
